# feat/arrays-l10n-v160prep 调查报告（概要）

面向：产品与维护决策。不含实现细节。

调查范围是 LogicSugar 仓库的 `feat/arrays-l10n-v160prep` 分支（当前版本自称面向 Mindustry BE 27771）。账号 AdvinxCNN 对该仓库有写权限。本工作区的规则与结论只留在本仓库，不进入全局。

---

## 结论先看

1. **再做一批「像 C++ STL」的结构：可以，但应克制。** 这个分支已经覆盖了最常用的那一层（数组、列表、栈、队列、堆、哈希表、位集、链表、记录，外加求和/排序等批量运算）。再往上堆树、字符串、迭代器，会很快撞上处理器容量和内存格限制，性价比差。值得做的是少量补齐（双端队列、集合、几条数组算法），而不是把 STL 整套搬进来。
2. **这些结构不适合当作普通用户函数，写进全局函数库文件里让人随便改。** 它们依赖「这张处理器上声明过的结构」，而全局函数库是所有处理器共用、且会改写调用方变量名的。可以在函数库界面里**只读展示**一份目录（让人知道有哪些操作、怎么写），但不要把内部实现塞进用户的函数库文件。
3. **超长程序只在退出编辑器时才报错，这个问题已经按调查结论改了。** 编辑过程中会显示当前编译后的长度对上限的占用；一旦超出会提示，并且关掉编辑器时会拦住，避免「关了才发现、还得再打开」。
4. **这个分支上的功能，并不只能活在 BE 上。** 保存出去的仍然是原版能跑的逻辑代码。最新正式版是 v8 Build 159.7。当前写成「最低 BE 27771」主要是发布口径和依赖选择，不是功能本身必须吃 BE 新指令。要在正式版上优雅提供：用正式版构建号做最低版本、单独出一条稳定产物即可。真正要小心的是「更新的 BE / 未来 v160」里内存读写语义可能变化，而不是 159.7 太旧。

## 1. 还要不要做更多 STL 式数据结构

### 这个分支已经有什么

玩家在编辑器里放一张「声明」卡片，就能在表达式里用比较接近平时写代码的方式操作内存：

- 一维数组、二维矩阵、数组初始化
- 记录（一组命名字段）
- 栈、队列
- 列表、小顶堆
- 哈希表
- 位集
- 链表
- 数组上的求和、平均、最值、计数、查找、填充、复制、升序/降序排序

它们的共同约定是：编辑器里好看、保存出去仍是原版逻辑。联机时没装本模组的客户端也能跑。

### 和 C++ STL 的对应（直观版）

| 常见 STL | 这个分支 | 建议 |
| --- | --- | --- |
| 定长数组 / 缓冲区 | 已有数组 | 保持 |
| 可变长度数组 | 已有列表（容量仍受内存格限制） | 保持 |
| 栈 / 队列 / 优先队列 | 已有 | 保持 |
| 哈希表 | 已有（数字键） | 保持 |
| 位集 | 已有 | 保持 |
| 链表 | 已有 | 保持 |
| 结构体 / 对 / 元组 | 已有记录 | 保持 |
| 双端队列 | 没有 | **值得做**，改动小 |
| 哈希集合 | 没有 | **值得做**，可复用哈希表 |
| 有序集合 / 红黑树 map | 没有 | **不建议**，指令太贵 |
| 字符串 | 没有 | **不建议**，逻辑语言几乎没有真正的字符串内存模型 |
| 迭代器、分配器、函数对象 | 没有 | **不要做**，模型对不上 |

还比较值得补的，是数组算法而不是新容器：倒序、替换、交换两个位置、在已排序数组上二分查找。并查集不是 STL，但在工厂逻辑里偶尔有用，而且相对便宜。

### 为什么不能「STL 越多越好」

处理器有硬上限（默认一千条指令，另外还有压缩后的体积上限）。复杂结构的一次插入、排序、探测，都会把预算吃掉。内存元格大约 64 格、内存库大约 512 格，再大的结构也没有地方放。此外，栈顶、队长这类运行状态在存档重新载入后会归零，内存格里的数字还在——这是现有结构已经存在的坑，新结构也会继承。

**建议：** 先补双端队列、集合、少量数组算法；把现有结构的说明做清楚。不要开树、字符串、图算法包这类大项目。

## 2. 能不能把 STL 和现有高级结构显示在全局函数库里

### 现在的函数库是什么

全局函数库是一份所有处理器共用的函数清单，玩家可以在里面自己写函数，所有处理器都能调用。它解决的是「这段子程序我想到处用」。

现有高级结构走的是另一条路：每张处理器上先声明「这块内存叫什么」，然后在表达式里写 `压栈`、`取值` 这种操作。编译器在保存时把它们展开成普通逻辑指令。这些内部实现**故意不写进**用户的函数库文件，以免被改坏、被带到别的机器上变成另一套语义。

### 三种做法

| 做法 | 能不能做 | 是否建议 |
| --- | --- | --- |
| 把内部实现写进用户的函数库文件，当作普通函数随便编辑 | 技术上能塞 | **不建议**。全局库看不到「这张处理器上声明过的数组」；库函数还会改名以免污染调用方变量，和结构绑定是冲突的 |
| 在函数库窗口加一页只读目录，列出已有操作和以后的 STL 操作 | 能 | **建议**。这是「显示在全局函数库里」最合适的理解：给人看、给人搜、给人复制写法，但不能改实现 |
| 另外提供不绑定声明、自己填写内存块和起止位置的通用函数 | 能 | **可作为高级选项**。给愿意手写地址的人用；日常仍应靠声明卡片 |

一句话：可以「出现在函数库界面里」，不可以「变成用户函数库文件里的普通函数」。声明卡片仍然是正确的主入口。

## 3. 编译后超过处理器上限时的提示

### 原来的问题

原版编辑器也是关掉才真正保存。这个分支会在保存时检查「编译后的指令是不是太多」，超了会报错并尽量留住草稿。但对使用者来说，感觉就是：**只有点退出的时候才爆红**，然后编辑器已经在关。

框选复制时如果卡片本身已经太多，会直接放弃复制，但那是卡片数量，不是编译后的真实长度。函数一展开、排序一类操作一带上，编译后往往比卡片数长。

### 这次已做的改动

- 编辑器底部持续显示「当前编译长度 / 上限」。
- 一旦超出，出现一次提示，并把数字标成警告色。
- 若绑定了具体处理器，也会盯压缩后的存储体积（游戏还有另一道体积上限）。
- 退出编辑器时若仍然超限，**拦住关闭**并说明原因（函数模式若是「内联」，会提示改回「普通」以共享函数体）。

这样超限会在编辑过程中被看见，而不是只在离开时才知道。

## 4. 能否在最新正式版上优雅实现（而不只是 BE）

### 版本事实

- 最新正式版：Mindustry **v8 Build 159.7**（约 2026-07-19）。
- 本分支发布说明要求 **BE 27771 或更新**。BE 编号来自开发构建流水线，时间上晚于 159.7，朝 v160 方向走。
- 仓库主线稳定版仍是 4.0.0、最低游戏版本 155；本分支把最低版本改成了 27771。
- 自动检查仍按较旧的正式快照拉游戏源码，说明功能代码并没有绑死在 BE 独有指令上。

### 判断

**可以在最新正式版上优雅提供。** 理由：

- 玩家保存的程序仍是原版逻辑，没装模组的客户端能跑——这是项目底线，BE 和正式版一样。
- 数组、数据结构、卡片本地化、断言调试等，主要是编辑器侧体验；正式版已经具备接管逻辑编辑器、注册自定义语句的能力。
- 本分支为「未来 v160」准备的那些游戏侧变化（内存里存单位/方块、官方卡片标题本地化等），正式版 159.7 **还没有**。本分支也没有把功能建立在那些新接口上。所以相对 159.7，是「用得到的都还在」；相对更新的 BE，反而要防内存越界读的语义变化。

不够优雅的只有**当前打包方式**：最低版本写成 27771，正式版根本不会加载这个 jar。

### 建议的发布策略

- **稳定线：** 最低版本对准最新正式版（159），用正式版验证，给大多数玩家用。
- **BE 线：** 继续用 27771+ 做体验版，单独标明。
- 两线可以共用同一套功能代码，差别主要在最低版本号和说明，而不是做两套数据结构。
- 等到正式 v160 再单独处理「内存能存对象、越界读不再是空数字」这类语义变化。

---

## 建议的下一步（按优先级）

1. 把本分支的稳定产物按正式版口径打一包，确认在 159.7 上加载与编辑都正常。
2. 函数库窗口加只读「内置结构操作」目录，不要改用户函数库文件格式。
3. 若继续做 STL：先双端队列、集合、倒序/替换/二分；不要开树和字符串。
4. 给现有结构补玩家能看懂的说明（尤其是：哈希表先清空、链表先初始化、状态不随存档保留）。
